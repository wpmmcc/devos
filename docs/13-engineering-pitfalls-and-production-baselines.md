# 文档 13：隐蔽工程坑、极简体验拼图与生产级底线设计（`13-engineering-pitfalls-and-production-baselines.md`）

前面已经把主干架构、协议、测试、更新和冲突隔离都定得很扎实了。真正进入落地开发和真实用户使用后，最容易让人返工的往往不是主流程，而是**边缘异常、安全攻击面和长期使用后的“慢性病”**。以下按你关心的三个维度，把最容易漏掉的关键点补齐。

---

## 一、开发实施阶段还要注意的 4 个隐蔽工程坑

1. **子进程“僵尸化”与孤儿进程清理**
* 应用运行期间会拉起大量子进程（本地预览代理、脚本运行器、日志流监听、`devos-mcp`）。如果桌面端意外崩溃或被用户在任务管理器强杀，这些子进程极易残留为孤儿进程，继续死占端口和文件句柄。
* **开发落地**：Windows 端将派生的子进程绑定到 **Job Object**（设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），macOS/Linux 端使用独立进程组（`setpgid`）并在主进程退出或收到信号时向整组发送终止信号，确保主程序一关、子进程全清。


2. **小白电脑的“非标准路径”地雷**
* 非开发用户的目录经常包含**中文、空格**（如 `C:\Users\张三\桌面\我的网站 1`）、**超长嵌套路径**（触发 Windows 260 字符 `MAX_PATH` 限制），或者直接建在了 **OneDrive / iCloud / 百度网盘同步目录**里。容器挂载同步盘目录极易导致 SQLite 锁死和 Docker 挂载崩溃。
* **开发落地**：新建项目向导默认将工作区设在纯英文短路径（如 `C:\DevOS-Projects` 或 `~/DevOS-Projects`）；若用户手动选了云盘同步目录或含特殊字符的路径，在建项前直接给白话风险提示并建议改路径。


3. **外部 Agent 写坏协议文件的“宽容解析与自愈”**
* 即使在 `AGENTS.md` 里再三强调通过 MCP/CLI 修改状态，实际使用中外部 Agent 仍可能直接用文件编辑工具去改 `devos.json` 或 `devos.run.json`，并写出带尾逗号、注释或漏括号的非法 JSON。
* **开发落地**：`devos-core` 读取项目 JSON 时采用宽松解析（支持 JSONC/尾逗号）+ 失败隔离——单个项目配置损坏时，**绝不能导致整个桌面端启动白屏**，而是在该项目的卡片上标出「配置文件格式异常」并提供「一键恢复上次正常备份」或「让 AI 修复格式」。


4. **内部快照不能污染用户自己的 Git 历史**
* 如果用 Git 做轻量代码快照，而用户项目本身也要推到 GitHub/Gitee，直接往当前分支打 commit 会把提交记录弄得一团糟；同时 `.devos/artifacts/` 里的截图和导出文件如果不隔离，很容易被误提交进仓库撑爆体积。
* **开发落地**：建项目时自动在 `.gitignore` 追加 `.devos/artifacts/`、`.devos/logs/` 和 `.env`；内部代码快照优先用独立隐藏 ref（如 `refs/devos/snapshots/...`）或独立暂存机制，保持用户主分支历史干净。

## 二、应用功能设计上容易漏掉的 5 块体验拼图

1. **面向小白的“密钥与环境变量（`.env`）”安全表单**
* 做 Web 或脚本项目几乎必然要填 API Key、支付配置或第三方 Token。小白看不懂 `.env` 语法，还经常不小心把真实 Key 直接贴在聊天里发给 AI。
* **功能建议**：在「项目资产」下增加一个极简的「密钥与配置」面板，以中文表单展示变量（值默认星号掩码）。约定**AI 只能读取 `.env.example`（结构说明），无权读取 `.env` 真实值**，既方便小白填配置又防密钥外泄。


2. **“一键撤销 AI 最近改动”的细粒度时光机**
* 提测前的快照颗粒度偏粗。实际使用中，小白经常在 Agent 改完一波代码后发现“还不如刚才的版本好用”，但又不懂 `git reset`。
* **功能建议**：在 Agent 调用关键写动作前（或按时间点）自动打一个极轻量的代码 Checkpoint，桌面端顶部提供一个低调但救命的「回到上一个版本」入口，能大幅降低小白的试错焦虑。


3. **跨会话的“Token 预算与上下文裁剪”**
* 项目做了一两周后，需求、知识库、已关闭 Issue 会越积越多。如果 `get_project_brief` 每次都把所有历史记录全量塞给 Agent，很快就会撑爆上下文窗口、拖慢响应速度甚至让模型注意力分散。
* **功能建议**：`get_project_brief` 默认只返回「项目概要 + 硬性标准 + 进行中/待测卡片 + 未关闭 Issue 摘要 + 最近 5 条知识标题」，详细内容由 Agent 按需再调接口查阅，保持单次握手返回控制在 2000–3000 Token 以内。


4. **项目的“导出交付、局域网预览与回收站”**
* **干净导出**：小白做完项目后常问“怎么发给别人或传到服务器”，提供一个「导出交付包（`.zip`）」功能，自动剔除 `.devos/` 临时文件、截图和本地 `.env`，附带一份自动生成的白话部署说明。
* **手机扫码预览**：做网页时经常要在手机上看排版，支持一键开启局域网预览二维码（把本地预览代理临时绑定到局域网 IP），同一 Wi-Fi 下微信/相机扫码即测。
* **项目回收站**：删除项目时默认移入系统回收站或归档目录，避免小白误点彻底删光几周的心血。


5. **零等待的“内置演示项目（Interactive Demo）”**
* 首次装完软件面对空看板，小白不知道下一步该干嘛。内置一个极简免拉大镜像的演示模板，引导用户在 1 分钟内走一遍「看预览 $\rightarrow$ 框选提 Issue $\rightarrow$ 看卡片流转」，比长篇帮助文档有效得多。

## 三、性能、安全与稳定性上的生产级底线

### 1. 安全底线（本地工具最容易翻车的 4 个攻击面）

* **防本地端口 CSRF 与 DNS Rebinding 攻击（高危）**：
* 守护进程监听在 `127.0.0.1:<port>`，且能执行容器命令。如果用户同时用浏览器访问了恶意网页，恶意 JS 可能通过构造请求或 DNS Rebinding 攻击本地端口，诱导执行任意命令。
* **防护**：本地 HTTP/IPC 接口强制校验三项——① `Host` 严格匹配 `127.0.0.1:<port>`；② 拒绝带非预期 `Origin` 的跨站请求；③ 所有接口强制校验 `Authorization: Bearer <token>`，且 `~/.devos/daemon.json` 在 Unix 下强制设置文件权限 `0600`（仅当前用户可读）。


* **防间接提示词注入（Indirect Prompt Injection）**：
* 预览探针抓回来的浏览器 Console 报错、HTTP 响应体，或后端脚本抓取外部网页的 `stdout`，都会打包进 `ISS-xxx.json` 喂给 Agent。外部网页若故意在报错文本中埋入恶意指令，可能诱导 Agent 越权操作。
* **防护**：`list_issues` 返回的外部日志与输出字段使用明确的数据边界标签（如 `untrusted_log_excerpt`）包裹，并在 `SKILL.md` 中声明这些字段仅作为排障数据，绝不可当作执行指令。


* **外部导入项目的“工作区信任（Workspace Trust）”**：
* 如果未来用户下载了别人分享的 DevOS 项目压缩包，里面的 `devos.run.json` 和 `.devcontainer` 可能包含恶意脚本。首次打开外部导入的项目时，必须弹出明确信任确认，未信任前禁止执行任何脚本、自动启动容器或运行 Hook。


* **截图与日志隐私提醒**：
* 自动截图可能拍到页面里的真实业务数据或个人隐私。提 Issue 弹窗里保留「预览截图 / 移除截图」按钮，让用户清楚发给外部 AI 的到底有哪些内容。



### 2. 性能底线（治“长期使用越用越慢”）

* **磁盘空间黑洞治理（Storage Cleaner）**：
* Docker 镜像层、DDEV 数据库快照、`.devos/artifacts/` 里的 PNG 截图与 Excel 测试产物，跑两个月轻松吃掉 30–50 GB，极易把 Windows C 盘撑爆。
* **方案**：在「设置 $\rightarrow$ 存储空间」提供可视化占用统计与「一键清理缓存」（按策略自动清理超过 30 天的已关闭 Issue 截图、过期脚本产物，以及带 `com.devos.managed=true` 标签的悬空镜像），磁盘剩余空间低于 5 GB 时主动弹温和提醒。


* **大文件与日志内存背压**：
* 后端脚本若陷入死循环每秒打印一万行日志，无限制读入内存会直接 OOM 崩掉 Tauri。读取子进程 `stdout/stderr` 必须做速率与总字节数截断（如前端实时流仅保留最后 2000 行，磁盘日志单文件上限 10 MB 滚动覆盖）。



### 3. 稳定性底线（极端异常下的自愈能力）

* **启动对账机制（Startup Reconciler）**：
* 面对电脑合盖休眠、突然断电、强杀进程等非正常退出，`daemon.json` 可能残留旧 PID，`port_leases` 残留僵尸端口，卡片可能卡在“运行中”。
* **方案**：应用每次启动时先跑一遍轻量对账——检查并清理已失效的锁与旧 PID，比对 Docker 实际运行中的 `com.devos.managed=true` 容器状态与本地状态库，以容器真实状态为准自动纠偏，让界面红绿灯永远说真话。


* **真正的异步取消链路（Cancellation Token）**：
* 容器拉镜像卡住或后端脚本死循环时，小白点「停止」不能只是把界面按钮重置，后台进程却还在偷跑吃 CPU。Rust 端所有长耗时任务必须绑定 `CancellationToken`，点击停止时同步终止容器内对应进程树并回收状态。


* **完全离线 / 弱网可用性**：
* 用户在高铁断网或 GitHub 无法访问时，启动体检、镜像测速、更新检查必须全部异步非阻塞且带短超时（2–3 秒），绝不能因为连不上外网就卡死在启动页，确保已初始化的本地项目在纯离线状态下依然能正常启动、预览、测试和记录反馈。



把这些隐蔽的工程坑、安全防线和长期维护机制在初期就写进核心骨架里，后续不管是自己迭代还是开源给社区协作，都会省掉大量“修完一个坑冒出三个坑”的返工成本。
